### 实施要点（实证修正了原计划的假设）

1. **`reload(server)` 不更新子模块绑定** → env 派生常量（`_ALLOWED_ORIGINS`/`_API_TOKEN`）留 server.py；
   子模块可变缓存（`_DEFAULT_CONFIG_CACHE`/`_CONFIG_SCHEMA_CACHE`/`_NAME_DICT_CACHE`）导出
   `reset_caches()`，由 server.py 在 import 段调用。
2. **`patch("server.X")` 只作用于「调用方查找名字的命名空间」** → patch 目标 = 被 patch 函数的
   **调用方所在模块**。生产调用方走 `from GalTransl.server import X` 的保持原样；
   由同域兄弟函数在新模块内调用的必须改到新模块。**共更新 13 处测试 patch 目标**。
3. **测试靠 `reload(server)` 重绑定第三方函数**（`test_logging_endpoints` patch
   `GalTransl.AppSettings.load_app_settings`）→ 子模块改**模块属性访问**
   （`from GalTransl import AppSettings` + `AppSettings.load_app_settings()`）。
4. **区间搬迁的两个机械陷阱**（均已修）：
   - 装饰器（`@dataclass`）位于 def 行之前，按 AST 行号切分会被漏掉 → 需按 `decorator_list` 起点切；
   - `self.` → `handler.` 的替换会误改同类兄弟方法调用 → 须改回裸名并补 `handler` 实参。

### 1.7 硬约束：三类「静默失效」陷阱（已实证）

这是本次重构**最大的风险**——出错不会报错，只会让测试**假通过**。

#### 陷阱 A：`importlib.reload(server)` —— 14 个测试文件

14 个测试文件（`test_endpoint_negative`、`test_build_output_newline`、`test_alt_translations_endpoint`、`test_dictionary_parse`、`test_cache_write_reject_while_translating`、`test_cache_replace_dry_run`、`test_cache_recheck_all`、`test_project_init_import`、`test_problem_check`、`test_logging_endpoints`、`test_h_scene_problem`、`test_server_security_smoke`、`test_review_ai_suggest`、`test_runtime_notices`）统一用：

```python
from GalTransl import server as _server_mod
importlib.reload(_server_mod)                        # ← reload 的是 server 模块本身
registry = _server_mod.JobRegistry()

```

**约束**：`serve` / `main` / `build_handler` / `JobRegistry` 必须在 `server.py` 中**定义**（不能只 re-export）。若 `build_handler` 被搬到 `server_handler.py` 而 server.py 仅 `from ... import build_handler`，`reload(server)` 后 server 命名空间里的绑定会指向旧模块对象，且 `ThreadingHTTPServer` 等间接依赖的 reload 语义全部改变 —— 测试行为不可预测。

#### 陷阱 B：直接属性赋值（非 patch）

```python

# tests/test_forjpresidue_parse.py:190 / :222
```

**约束**：被赋值的名字，必须与其**调用方实际读取的命名空间一致**。
- `_common_dict_directory` 的调用方是 `_ensure_common_dicts_in_config` → 二者必须同模块，否则赋值被静默忽略（测试仍"通过"，但测的不再是原意）。

> **② 同域互调函数不跨模块**（见 §2 模块划分的「不可拆分簇」）。
> **③ `serve`/`main`/`build_handler`/`JobRegistry`/`INDEX_HTML`/`_ALLOWED_ORIGINS`/`_API_TOKEN`/`ThreadingHTTPServer` 定义在 `server.py`**（陷阱 A）。
> **④ 少量被 patch 且无法保持同模块的函数，同步更新测试的 patch 目标**（清单见 §3，需用户裁决 —— 见 §5）。

#### 实证验证（2026-09-20 实测，修正了原假设）

本轮用最小复现工程实测了 Python 的 `importlib.reload` 与 `mock.patch` 在「server.py re-export 子模块」结构下的真实语义，**结论比原判断更严格**：

**实测 1：`reload(server)` 不会更新子模块的绑定**

```
1) 初次:                      sub:default  const:default
2) reload(server) 后:         sub:default  const:default   ← 未更新！
3) 仅 reload(sub) 后:         sub:CHANGED  const:default
4) 再 reload(server) 后:      sub:CHANGED  const:CHANGED
```

→ **任何「依赖环境变量 / 需要在 reload 时重新求值」的模块级常量，都必须留在 `server.py` 求值**。否则 `reload(server)` 拿到的仍是子模块首次导入时的旧值。

**实测 2：`patch("server.X")` 对拆分到子模块的调用方不生效**

```
== patch("pp.server._run_problem_detection") ==
 同模块 recheck()       : recheck<REAL>   ← 未生效（真实实现）
 跨模块 recheck_cross() : cross<REAL>     ← 未生效
 外部 call_server_ns()  : caller<MOCK>    ← 生效（调用方读 server 命名空间）
 外部 call_sub_ns()     : caller_sub<REAL>← 未生效
```

→ **patch 只影响「调用方查找该名字的命名空间」**。函数一旦搬到子模块，`patch("GalTransl.server.X")` 对子模块内部的调用**必然打空**，且**测试仍会通过**（用真实实现跑完）。这使 §5 裁决点③从「可选」变为**必须**。

## 五、裁决结果（2026-09-20 用户批准「所有都按你推荐的来」）

> 用户指示：「所有都按你推荐的来」。以下按推荐方案执行，并**修正了方案内部的一处矛盾**。

### 裁决点 ①：`build_handler` / `JobRegistry` 是否允许离开 server.py？

**裁决：不允许。** 二者定义在 `server.py`。提交 10/11 只把**路由块内容**委托到 `server_handlers_*.py`，`build_handler` 函数本体与 `RequestHandler` 类壳留在 server.py。

**依据（实测强化）**：14 处 `importlib.reload(server)` 后直接调用 `_server_mod.build_handler(registry)`；实测 1 证明 `reload(server)` 不会更新子模块绑定，若 `build_handler` 搬走，reload 语义将不可预测。

### 裁决点 ②：是否把 `JobRegistry` 也搬到 `server_jobs.py`？

**裁决：搬到 `server_jobs.py`，并同步改 2 处测试 patch 目标**（`test_job_registry_prune_and_resize.py:57`、`test_job_submit_overrides.py:33` 的 `GalTransl.server.run_job` → `GalTransl.server_jobs.run_job`）。

**修正说明（原方案自相矛盾，已厘清）**：我在 §5 原推荐「搬到 server_jobs.py」，同时裁决点 ① 又说「定义在 server.py」——二者直接冲突。**最终口径（唯一解释）**：
- **`JobRegistry` 类定义在 `server_jobs.py`**（真身）；
- **`server.py` 通过 `from GalTransl.server_jobs import JobRegistry` 绑定**；
- 实测 1 已证明该绑定在 `reload(server)` 时会**重新执行 import 并取到子模块当前对象**（第 4 步 `const:CHANGED` 即证），因此 14 处 `_server_mod.JobRegistry()` 在 reload 后**仍可用**；
- 与 `build_handler` 的区别：`build_handler` **不搬**，因为它是「服务器壳」且其内部引用了 `INDEX_HTML` 等需在 server 命名空间解析的名字；`JobRegistry` 是纯类，无 env 依赖，搬走安全。

### 裁决点 ③：被 patch / 直接赋值的函数，是否允许同步更新测试？

**裁决：允许同步更新测试的 patch 目标（9 处）。**

**依据（实测 2 使其成为必须）**：`patch("GalTransl.server.X")` 对搬到子模块的调用方**必然打空**且测试仍通过（静默假通过）。若不允许改测试，则所有相关 patch 都失去意义。

**统一处理口径**：
1. **测试侧**：`mock.patch("GalTransl.server.X")` → `mock.patch("GalTransl.<新模块>.X")`；`patch.object(_server_mod, "X")` → `patch.object(<新模块>, "X")`；直接赋值 `_server_mod.X = ...` → `<新模块>.X = ...`。
2. **`GalTransl/` 内 7 个文件的生产调用方**：import 路径**零改动**（继续 `from GalTransl.server import X`）。原因：这些是生产代码，改路径会扩大改动面；且无 patch 依赖它们（patch 打的是测试的调用方，不是生产调用方）。
3. **server.py 对搬走的符号做真实绑定 re-export**：`from GalTransl.<新模块> import X`（不用转发函数——转发函数会让 `patch("GalTransl.server.X")` 打到转发壳上，同样失效）。

> **注**：`test_forjpresidue_parse.py:190/222` 的 `srv_mod.record_runtime_error = _fake_record`（`record_runtime_error` 本就属 server_runtime.py，不参与本次搬迁）**无需改动**——它赋值的目标本来就是 server.py 命名空间，且调用方 BaseEngine 走 `from GalTransl.server import record_runtime_error`，行为不变。

### 统一执行口径（最终）

| # | 口径 | 依据 |
|---|---|---|
| 1 | 生产调用方 `from GalTransl.server import X` **零改动** | 缩小改动面；无 patch 依赖 |
| 2 | server.py 对搬走的符号做**真实绑定 re-export**（`from <mod> import X`） | 不用转发函数，否则 patch 失效 |
| 3 | 同域互调函数**不跨模块** | 实测 2：跨模块调用 patch 不生效 |
| 4 | `build_handler` / `RequestHandler` 壳 / `serve` / `main` **不搬** | 实测 1：reload 语义 |
| 5 | `JobRegistry` **搬**，server.py re-export | 实测 1：re-export 绑定随 reload 刷新 |
| 6 | env 派生常量（`_ALLOWED_ORIGINS`、`_API_TOKEN`）**不搬** | 实测 1：需随 reload 重算 |
| 7 | 可变状态与其使用者**成对搬** | 避免循环导入 |

| 9 | 9 处测试 patch 目标**同步更新** | 实测 2：否则静默失效 |
