## 已同步

### PR #211 单句过长检测（提交 3e714fa）

上游「单句过长」即本地「长句丢失换行」（`CProblemType` 枚举位同为 13），本地实现为超集：
多了 H 场景专用阈值（`avgSentenceLengthThresholdH`，默认 24）、真实/字面换行归一化
（`_newline_count`/`_clean_text_len`）、「原文有换行才检测」门控。检测逻辑不移植，仅取上游
加固的阈值取值守卫：新增 `_coerce_positive_int()`，修复本地 `int()` 弱转换的 4 个 bug：

1. `int("1_000")` = 1000（Python 接受下划线字面量，前端拒绝，前后端口径不一致）
2. `int(True)` = 1（YAML 写 `true` 静默变成 1，无回退）
3. `int(17.9)` = 17（静默截断非整数，前端 Number.isInteger 会拒绝，口径不一致）
4. 阈值写 0 / 负数直接生效（`avg > 0` 恒真 → 全量误报「长句丢失换行」）

同一弱转换模式存在于 4 个 getter（平均/H/定语/状语阈值），已用同一守卫收口。
测试：`tests/test_problem_threshold_guard.py`（16 例）。

遗留（随桌面端暂缓项处理）：本地桌面端 `ProjectConfigPage.tsx` 的读取守卫
（`typeof raw === "number" && Number.isFinite(raw)`）仍接受非整数与 0/负数，
后端加固后两端口径在非法值上仍有差异，建议桌面端对齐时一并收紧。

## 暂缓项评估

### 1. API 客户端韧性重构（61552bb，上游 BaseTranslate.py 530→1346 行）

内容：传输层错误分类（`_is_transport_error`）、连续 3 次连接错误自动重建 API 客户端
（`_recycle_failed_client`，带 asyncio.Lock）、`maxApiRetries` 可配置（默认 6，拒绝解析
失败不再消耗 API 重试预算）、chatbot 状态改 ContextVar（协程隔离）、连接池加上限
（max_connections=100，pyreqwest 空闲 30s 回收）、批次翻译失败不再整体重试而是标记
(Failed) 占位、shutdown 补收 retired clients。

移植难度：**高**。上游基于其重写后的 ask_chatbot（attempts 预算模型），本地 BaseTranslate.py
只有 533 行且重试/健康度机制已独立演进（RequestHealthMetrics、可中断睡眠、JobCancelledError）。
不能直接取上游文件，需按功能逐项对齐本地实现。

建议优先级：**高**（客户端自动回收和 maxApiRetries 解决死端点卡死 worker 的实际问题，
批次失败占位避免重复请求烧 token）。移植时注意：与本地取消中断（stop_event）交互、
重试计数口径（本地 api_try_count 同时驱动 token 轮换）、`record_runtime_error` 的本地签名。
