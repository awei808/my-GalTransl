## §0.1 版本切分的价值（为什么这样切是对的）

| 版本 | 内容 | LLM 风险 | 依赖 |
|---|---|---|---|
| 0.5.0 | 四项功能 | **无**（全是确定性数据流改造） | 无 |
| 0.6.0 | Agent + MCP | **高**（新引入 LLM 决策） | 依赖 0.5.0 的流水线可配 + 注入块可配 |
| 0.6.1 | H 过滤 + token 限制 | 无（纯守卫） | 依赖 0.6.0 的 agent 工具链 |

**关键收益**：0.5.0 可独立发布并验证，即使 agent 延期也不阻塞。且 0.6.0 的 agent 工具（`start_translation` 等）**必须**依赖 0.5.0 的流水线可配能力，顺序天然成立。

```
人： 指定流程（选文件 + 选指令 + 划路线）
AI： ├─ 执行命令（调用翻译后端跑流水线）
     └─ 验收（判断哪些文件需要校对润色 → 执行对应命令）
```

**关键推论**：B 方案需要 LLM 决策，因此：

- 必须实现 **function-calling 主循环**（工具调用 → 结果回灌 → 继续推理）
- 必须实现 **权限门禁**（因为 LLM 会自主决定要不要读 H 文本、要不要写缓存）
- 必须实现 **token 预算守卫**（LLM 多轮会累积消耗）
- 但**不需要**：子代理并行、上下文自动压缩、长等待（这些是"全自主 agent"才需要，见 §5 丢弃清单）

### 0.2 B 方案下 Agent 的职责边界

```
人： 指定流程（选文件 + 选指令 + 划路线）
AI： ├─ 执行命令（调用翻译后端跑流水线）
     └─ 验收（判断哪些文件需要校对润色 → 执行对应命令）
```

**关键推论**：B 方案需要 LLM 决策，因此：

- 必须实现 **function-calling 主循环**（工具调用 → 结果回灌 → 继续推理）
- **0.6.1 必须实现权限门禁**（因为 LLM 会自主决定要不要读 H 文本、要不要写缓存）
- **0.6.1 必须实现 token 预算守卫**（LLM 多轮会累积消耗）
- 但**不需要**：子代理并行、上下文自动压缩、长等待（这些是"全自主 agent"才需要，见 §4 丢弃清单）

### 0.3 MCP 的定位（0.6.0 同期做）

MCP 与内置**共用同一份工具定义**（`tool_schema.py`）。内置先落地，MCP 作为派生层同版本交付，二者不是二选一。**但 H 门禁与 token 限制只在内置侧生效**（0.6.1）。

### 2.3 权限门禁设计（基础版 0.6.0；H 读门禁 0.6.1 —— 本项目独有）

**三级风险 + fail-closed**（借鉴上游，但**必须扩展"读"维度**）：

```
风险档：
  read_public    ── 自由读（项目概况、文件清单、问题统计）
  read_sensitive ── ⚠️ 本项目独有：读 H 区间原文需审批
  edit           ── 写缓存/字典/人名表，需审批
  high           ── 启停翻译/改配置/删缓存，需审批
```

**H 读门禁实现**（复用现有基建，非从零造）：

- 现有基建：`ForGalJsonTranslate.py:1123-1137` 的 **H 强度 4 档**（`intimate`/`explicit` 为 h ≥ 0.5）+ `:1201-1234 _resolve_h_check_words` 读 `forbiddenDictH`/`hCheckDict`
- 数据来源：`metadata.py:462 BatchMetadata` 已含**区间 + h 档位**，`segments_in_range`（L482）可按行号区间查询
- 实现：`read_input_file` / `read_transl_cache` 在返回前，查目标行号区间是否落在 `h ≥ 0.5` 的语义段内
  - 命中 → 走审批（用户可选"拒绝"→ 返回**空内容** / "同意"→ 返回**完整内容**）
  - 未命中 → 直接返回
- **这是上游完全没有的能力**（上游 `read_input_file` runtime.py:4184 直接返回原文，零过滤）

### 2.4 token 预算守卫（严格按用户口径：只限程序内 API）

**口径**：只约束本项目 `COpenAITokenPool` 发起的调用；外部 agent 的花费不在管辖范围。

**实现**（`token_budget.py`）：

- 借鉴上游 `2302-2477` 的**中文 token 估算**（`_chars_to_tokens` / `_estimate_text_tokens`，中文按多字节折算，修正上游早期低估 bug）
- 三处守卫：
  1. **单轮请求前**：估算 `messages + tools schema` 的 token（借鉴 `:2426 _tools_overhead_tokens`），超上下文窗口则拒绝并发错误提示
  2. **会话累计**：记录本会话累计消耗，超预算上限则暂停并提示
  3. **轮数上限**：`max_turns` 硬上限（防死循环烧 token）
- 配置项走 `DEFAULT_PROJECT_CONFIG_YAML`（新增 3 个键，自动进 schema）

### 3.1 流水线不再固定、可修改

**目标**：阶段可增删改序、每个阶段可独立选后端。

**方案**：抽成**单一来源的阶段清单**

1. **新建** `GalTransl/Frontend/pipeline_stages.py`：定义阶段清单数据结构

```python
@dataclass(slots=True)
```

### 3.4 剧情路线图可视化编辑（0.5.0 重点）

**目标**：**在可视化界面上直接编辑**（拖拽节点、连线构建路线），而非仅编辑文本源码。

**现状核查（关键澄清）**：

现有 `PlotRoutePanel.tsx` 提供的是"**文本可编辑 + 可视化预览**"——在 mermaid 渲染出的 SVG 上挂点击事件（`el.addEventListener("click", ...)`），点击后弹窗改节点名，再**用字符串替换回写源码**：

```typescript
// PlotRoutePanel.tsx:284 saveNodeEdit
const target = hasQuoted ? `${ed.alias}["${quoted}"]` : `${ed.alias}[${ed.label}]`;
// 防护：节点定义行必须能在源码中找到，否则替换无效（代码自己的注释已承认脆弱）

  toast.warning("未能在源码中找到该节点，无法保存修改");
  return;
}
```

**这不能满足需求**：无法拖拽节点、无法连线、无法增删节点、无法调整布局。

#### 3.4.1 开源库选型调研结论（2026-09-21 实测）

| 候选 | 能力 | 许可 | 问题 | 结论 |
|---|---|---|---|---|
| **`interactive-mermaid`** | **仅拖动已有节点位置** + 位置 localStorage 持久化 | MIT | ❌ **不能连线、不能增删节点、不回写 mermaid 源码**；且依赖 `beautiful-mermaid`（另一个渲染库，非 mermaid.js） | ❌ 不满足 |
| **`@dschz/solid-flow`** | SolidJS 版 React Flow 移植；拖拽/连线/多选/`Background`/`MiniMap`/`Controls` 全有 | MIT | ⚠️ **alpha 阶段**（v0.2.6，JSR 仅 9 次/周下载），API 可能变动；`onlyRenderVisibleElements`/自定义 MiniMap/边重连**未实现** | ⚠️ 可用但风险高 |
| **`@xyflow/svelte`（Svelte Flow）** | 与 React Flow 功能对等，MIT，**230K 周安装**，v1.6.x 稳定 | MIT | ⚠️ **绑定 Svelte**，本项目是 SolidJS，需跨框架嵌入 | ⚠️ 需额外方案 |
| **`solid-flow`（miguelsalesvieira）** | SolidJS 节点编辑器 | MIT | ❌ **2022 年最后更新**（v1.0.4），158 star，已停维护 | ❌ 不采用 |
| **自绘 SVG 交互层** | 完全可控 | — | 工作量大（连线算法、命中测试、布局） | 备选 |

**核心矛盾**：mermaid.js 是**渲染库不是编辑库**——它单向把文本编译成 SVG，SVG 布局由内部 dagre 引擎计算，**不支持反向编辑**。要做可视化编辑必须换掉渲染层。

#### 3.4.2 推荐方案：**双模式并行**（分层解耦，风险最低）

```
┌─────────────────────────────────────────────────┐
│  编辑模式（可视化）—— @dschz/solid-flow          │
│  · 拖拽节点、拉线连接、多选、增删                │
│  · 节点 = 一个剧情段落/路线                       │
│  · 边   = 剧情流向                                │
└────────────────┬────────────────────────────────┘
                 │ 双向转换（本项目自研，~300 行）
┌────────────────▼────────────────────────────────┐
│  数据中枢：PlotRouteMap.json（结构不变）          │
│  { 结构类型, 用户大纲, mermaid, 文件归属, 节点剧情 } │
└────────────────┬────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────┐
│  预览模式（只读）—— 现有 mermaid.js 11.16.1      │
│  · 保持现状，供翻译注入链路与快速预览使用         │
└─────────────────────────────────────────────────┘
```

**为什么双模式**：
1. **保护现有资产**：`mermaid` 字段是 `PlotRouteMap.json` 的既有字段，且被 `context.py:189/210` 注入翻译提示词——**后端依赖不能断**。编辑模式产出仍需回写为 mermaid 文本。
2. **降低风险**：`@dschz/solid-flow` 是 alpha，若将来 API 破坏，只影响编辑模式，预览与后端注入不受影响。
3. **符合项目架构**：现有前端已有"源码/预览分栏"（`PlotRoutePanel.tsx`），扩展为三态（可视化编辑 / 文本 / 预览）是自然演进。

**新增转换层**（本项目自研，`desktop/src/lib/plotRoute/`）：

| 文件 | 职责 | 估算 |
|---|---|---|
| `flowToMermaid.ts` | Flow 节点/边 → mermaid 源码 | ~150 行 |
| `mermaidToFlow.ts` | mermaid 源码 → Flow 节点/边（解析 `flowchart TD` 的子图/节点/边） | ~150 行 |
| `routeLayout.ts` | 自动布局（初始布局建议用 dagre，即 mermaid 内部同款引擎） | ~100 行 |

**风险与规避**：

| 风险 | 规避 |
|---|---|
| `@dschz/solid-flow` alpha，API 变动 | 转换层做**适配隔离**，Flow 库只出现在 `PlotRoutePanel` 与其子组件；锁定版本（`package.json` 精确版本号，不用 `^`） |
| mermaid ↔ Flow 转换丢信息（子图嵌套、样式类） | **只支持必要子集**（`flowchart TD` + `subgraph` + 节点 + 边 + 节点标签）；转换失败时降级到文本编辑模式并提示 |
| 节点 id 不稳定导致接线错乱 | 转换层维护 **alias ↔ node id 映射**（复用现有 `文件归属` 的 alias 概念） |
| 引入新库导致包体积膨胀 | 评估 `@dschz/solid-flow` 产物体积；若过大，退回"自绘 SVG 交互层"（备选方案） |

**待用户确认（新增）**：是否接受引入 `@dschz/solid-flow`（alpha）？备选是自绘 SVG（可控但要自研连线算法，工作量约翻倍）。

#### 3.4.3 其余改造点

1. **多选文件**：⚠️ `SidebarPanel.tsx:64` 的 `selected: string | null` 是**单选**，**无多选逻辑可复用**，需新建 `Set<string>` 多选状态
2. **与 agent 联动**（0.6.0）：多选文件 → 加到右侧 agent 面板 → 选指令 → 触发翻译/分析
3. **后端按路线梳理**：`batch_translate`（`ForPlotRouteMap.py:228`）已支持 `structure_type` / `user_outline`；新增"按用户划好的 `文件归属` 逐路线梳理 `节点剧情`"模式（增量，不重新划分结构）

| 风险 | 影响 | 规避 |
