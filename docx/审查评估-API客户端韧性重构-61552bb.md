# 审查评估：上游 61552bb「API 客户端韧性重构」（2026-09-11）

审查对象：上游提交 `61552bb`（Improve API client resilience & retry config，xd2333，2026-09-05）。
对照基准：本地 fork 架构。**关键前提：上游该提交全部落在单层的 `BaseTranslate.py`（1346 行），
本地已把客户端层拆到 `GalTransl/Backend/BaseEngine.py`（1310 行，ask_chatbot/init_chatbot/shutdown 所在），
`BaseTranslate` 只承载翻译流水线。移植落点必须是 BaseEngine，不能按上游文件位置搬。**

## 一、上游实现本身的审查发现

### 值得肯定的设计
- `_is_transport_error` 分类合理：只把 `APIConnectionError / APITimeoutError / httpx.TransportError /
  TimeoutError / ConnectionError / OSError` 视为连接层错误，刻意排除 5xx（`InternalServerError`）
  与 `RateLimitError`，避免认证/配额/服务端错误引发无意义的客户端重建。
- `_recycle_failed_client` 并发控制正确：asyncio.Lock 串行化、按对象身份（`is`）匹配配对防误换、
  旧客户端移入 `_retired_clients` 持引用（顺带防了 `id()` 复用）、shutdown 时统一关闭。
- attempts 预算与轮换偏移拆分（`api_attempts` vs `api_try_count`）修了上游真实 bug：
  其 ForGalJsonTranslate 传 `base_try_count=retry_count`，旧口径下解析重试会吃掉 API 重试预算。
  **本地无此 bug**（grep 证实本地没有任何调用方传 `base_try_count`），此项本地无移植对象。

### 问题
1. **配置注释与实际语义不符（口径）**：`DefaultProjectConfig` 写「maxApiRetries: 单个批次最多调用
   API次数，达到上限后标记失败并继续后续批次」。实际是「ask_chatbot 单次调用的尝试预算」；
   上游 ForGalJsonTranslate 的外层解析重试循环仍无上限（retry_count 无 cap），"批次最多 6 次"
   并不成立。移植时注释必须写准确。
2. **429 消耗尝试预算值得质疑**：上游 except 路径里 RateLimitError 也 `api_attempts += 1`。
   429 是暂时性限流，指数退避本来就能恢复；6 次预算在持续限流下很快耗尽并把批次标失败，
   与「重试到成功为止」的存量用户预期冲突大。这是移植时需要拍板的设计决策
   （可选：429 不计入预算但设独立上限，或默认值调大）。
3. **连接池上限是隐性行为变更**：`_build_http_client` 把 `Limits(None, None)` 改为
   `max_connections=100 / keepalive 20 / keepalive_expiry=30s`，pyreqwest 路径加
   `pool_idle_timeout=30s / pool_max_idle_per_host=20`。30s 空闲过期是真正收益
   （自愈"指向已重启网关的僵尸空闲连接"）；100 上限对单 client（单 token 单引擎实例）足够，
   但需在变更说明中标注，高并发用户报"池等待"时知道回退点。
4. **失败计数以 `id(client)` 为键**：自洽性依赖 `_retired_clients` 持引用这一隐式不变式
   （对象不被 GC 则 id 不复用）。当前代码成立但脆弱，移植时建议改用 `(client, token)` 对象引用
   或在注释里钉死该不变式。
5. **状态双写残留**：上游同时写实例属性 `_last_chatbot_was_stream/_last_chatbot_model_name`
   和新 ContextVar（兼容旧测试/插件）。本地已是纯 ContextVar + getter（`BaseEngine.py:60-61,709-715`），
   移植时不要带回双写。
6. `asyncio.Lock()` 在同步 `__init__` 创建：Python 3.10+ 安全（本地要求 3.11+），无问题。
7. `OSError` 入分类偏宽（非网络 IO 错误也命中），但该上下文异常仅来自 API 调用路径，可接受。

## 二、与本地现状的功能矩阵（上游 9 项改动逐项判定）

| 上游改动 | 本地现状 | 判定 |
|---|---|---|
| ContextVar 请求状态隔离 | 已有且更干净（纯 CTX，无实例属性回退） | **不移植** |
| 重试路径用 `_interruptible_sleep` | 已有（BaseEngine:597，退避/RPM 全在用） | **不移植** |
| 批次异常标 (Failed) 兜底 | 已有等价机制且架构不同：ForGalJsonMulitChat.translate 已捕获 LLM 异常（:1321-1340，记 kind="llm" 运行态→空响应走失败兜底），本地失败策略是 retain_failed=False（失败句不保留、留待下次运行，:718），与上游"标 (Failed) 入缓存"策略相反 | **不移植**（策略冲突） |
| `genDicMaxApiRetries` 配置 | **本地已实现同名配置**（GenDic.py:546，:812/:1065/:1320 消费） | **不移植** |
| GenDic 提前 return 漏 shutdown | 本地 GenDic 分支有 shutdown（LLMTranslate.py:584）但**未包 try/finally**：batch_translate 抛出（如取消）时跳过关闭，客户端泄漏 | **移植（本地等价 bug 真实存在，最小改动）** |
| `_is_transport_error` 分类 | 无 | **移植** |
| 客户端失败计数 + 自动回收 + retired 清理 | 无 | **移植（核心收益一）** |
| `maxApiRetries` 尝试预算 | **翻译轮无上限**：ForGalJsonMulitChat:396 不传 `max_retry_count` → ask_chatbot 内无限退避重试（单次上限 2^6+jitter≈64s），仅可手动停止；本地可选熔断 apiMaxErrorRate/apiMaxRequests 默认关闭。GenDic/元数据引擎已各有预算（3 次） | **移植（核心收益二，需拍板默认值与 429 语义）** |
| 连接池上限 + 30s 空闲回收 | 无（无限连接） | **可选移植（建议取）** |

补充：本地 `BaseEngine._coerce_positive_int`（:299-305）是 clamp 语义（`max(1, int(value))`，
接受 bool/下划线/非整数截断），与本次刚移植到 ConfigHelper 的严格守卫同名不同义。
若给 maxApiRetries 用 clamp 版，`0→1`（一次即败）、`"1_000"→1000`、`true→1`，口径与前端冲突；
GenDic 的 genDicMaxApiRetries 现也在用 clamp 版。**移植时应统一用严格守卫**（顺带修 GenDic 同类口径，
但注意 clamp→回退是行为变更，需评估存量写了 0 的项目）。

## 三、移植方案（分步，按风险递增）

1. **D1（先行，低风险）**：GenDic 分支 shutdown 包 try/finally + 取消路径测试。
2. **D2（核心）**：BaseEngine 新增 `_is_transport_error`、失败计数、`_recycle_failed_client`、
   shutdown 扩展关闭 retired clients。回收逻辑需要与 init_chatbot 共用客户端构建，建议顺势抽
   `_build_http_client`（保留本地 pyreqwest/代理分支结构）。插入点建议放在
   `_check_error_rate_quota()` **之后**（上游放在 health 记录之前——熔断终止时不必白建客户端，
   本地有熔断机制，顺序差异是有意的）。测试：移植上游"回收"与"状态隔离"两用例到本地测试布局。
3. **D3（核心，需拍板）**：翻译轮 `maxApiRetries`：init_chatbot 读取（严格守卫）；
   ask_chatbot 双计数（`api_attempts` 预算 / `api_try_count` 轮换偏移）；
   `max_retry_count=None` 时回退实例默认（显式传参优先，GenDic/元数据不受影响）。
   决策点：a) 默认值（上游 6；建议本地 8~10 缓和"无限重试→6 次失败"的行为跳变）；
   b) 429 是否消耗预算；c) api_logger.record 的 retry_count 字段记 attempts 还是轮换偏移。
   链路确认：预算耗尽抛 RuntimeError → 多轮 translate 既有 except 兜住 → 失败兜底（不保留）→
   `_batch_translate_common` stall 3 轮跳批。**链路闭合，无需移植上游批次兜底。**
4. **D4（可选，随 D2）**：连接池上限 + keepalive 30s（僵尸连接自愈），变更说明标注回退点。
5. **D5（可选，低优先级）**：ask_chatbot 前 `_clear_chatbot_state`，防跨请求读到 stale 模型名。

## 四、结论

上游该提交方向正确、核心两功能（客户端回收、尝试预算）解决本地真实存在的"死端点卡死 worker"
问题，值得移植；但其价值密度低于行数观感——9 项改动中 4 项本地已有等价物或无移植对象，
1 项（批次 (Failed) 标记）与本地失败保留策略直接冲突不可照搬。真正要写的新代码集中在
BaseEngine 的分类/回收/预算三块，上游实现可参照但需按本地熔断、api_logger、TTFT 状态灯、
JobCancelledError 等既有机制重新编排插入点。先行 D1 是独立小修。
