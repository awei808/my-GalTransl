## §1 缺陷一：启动流程 `NameError: _run_full_pipeline`（0.5.0 必崩）

### 1.1 根因

`GalTransl/Frontend/LLMTranslate.py:194` 的 `await _run_full_pipeline(...)`。该函数本体在 0.4.10 拆分时迁至 `Frontend/llm_pipeline.py:582`，但 LLMTranslate 顶部 45–80 行的 re-export 区块**漏了这一项**（`_run_gendic_flow`、`preprocess_trans_list` 等兄弟符号都在）。

文件末尾 1330 行的 PEP 562 模块级 `__getattr__` **兜不住**：它只对 `模块.属性` 访问生效，不参与函数体内的全局名查找。

### 1.2 证据

| 证据 | 内容 |
|---|---|
| 运行时实证 | `'_run_full_pipeline' in vars(LLMTranslate)` = **False**；`hasattr(...)` = True；该名字在 `doLLMTranslate.__code__.co_names` 中 → 运行必抛 NameError |
| PEP 562 语义实证 | 临时模块最小复现：`m._hidden()` 成功、`m.g()`（函数内调 `_hidden()`）抛 `NameError` |
| 现场日志 | `release/GalTransl_0.4.9_win/理狂人/error.log` `[2026-09-22T09:02:18Z]`（= 本地 17:02:18，对应 `GalTransl.log:1182`「当前版本: 0.5.0」）：`Service.py:308 → Runner.py:368 → LLMTranslate.py:194` |

### 1.3 为什么 1602 个测试全绿也没抓到

- `tests/test_refactor_contract.py:129` 用 `hasattr(LLMTranslate, name)` → 走 `__getattr__`，通过；
- `tests/test_runtime_notices.py:150` 用 `from GalTransl.Frontend.LLMTranslate import _run_full_pipeline` → 同样走 `getattr`，通过；
- **唯一没被覆盖的正是函数体内的全局名查找，也就是唯一的生产路径。**

### 1.4 改动方案

| 文件 | 改动 |
|---|---|
| `GalTransl/Frontend/LLMTranslate.py` | 顶部 re-export 区块补 `from GalTransl.Frontend.llm_pipeline import _run_full_pipeline`；在 1330 行 `__getattr__` 的 docstring 注明「仅兜外部属性访问，函数体内引用必须走模块级导入」 |
| `GalTransl/Frontend/llm_pipeline.py` | 模块 docstring 补一句约束：**禁止**模块级 `import LLMTranslate`（现为函数内延迟导入，557 行） |

**循环依赖已核实可排除**：llm_pipeline 顶层仅 import `LOGGER / ConfigHelper / server_runtime / llm_runtime / llm_prepost / pipeline_stages`；其中 llm_runtime、llm_prepost、pipeline_stages 均不 import LLMTranslate，llm_pipeline 自身只在函数内延迟导入。

### 1.5 潜在 bug 与防范

| 潜在问题 | 防范 |
|---|---|
| 头部 import 后，将来有人在 llm_pipeline 加模块级 `import LLMTranslate` → 真环 | 在 llm_pipeline docstring 写明约束（§1.4） |
| 只补符号不补测例 → 同类回归再次逃逸 | 契约测试从 `hasattr` 改为 `name in vars(module)`（见 §1.6） |
| 保留 `__getattr__` 可能继续掩盖同类问题 | 保留（兼容既有外部引用面），但 docstring 标注局限 |

### 1.6 测例

| 层 | 测例 |
|---|---|
| 契约（关键） | `test_refactor_contract.py`：`test_all_top_level_symbols_present` 的 `hasattr` 改为 `name in vars(LLMTranslate)`（**这一改就能挡住同类回归**）；新增断言 `LLMTranslate._run_full_pipeline is llm_pipeline._run_full_pipeline` |
| 端到端 | 新增用例：真调 `doLLMTranslate`（mock 掉 `ensure_model_available_if_needed` 与 `_run_full_pipeline` 内部实现），断言不抛 NameError 且确实调用到 llm_pipeline 的实现 |

### 1.7 日志

无需新增。NameError 经现有 `Service.run_job_async` 的异常路径写入 `error.log`（已验证有效）。

## §2 缺陷二：模型输出慢时 check-model 报「请求超时」

### 2.1 根因（两段）

| 段 | 位置 | 问题 |
|---|---|---|
| 前端 | `desktop/src/lib/api/client.ts:49` + `lib/api/general.ts:138` | `apiRequest` 默认 **30s** AbortController；`checkModelAvailability` **未传 `timeoutMs`** → 到点 abort，抛 `ApiError("请求超时：${baseUrl}${path}", 408)`（client.ts:62-64）。全仓仅 `lib/api/project.ts:455` 用了 `timeoutMs: 120000` |
| 后端 | `server_handlers_project.py:142` → `server_backend.py:167` → `COpenAI.py:280` | 探活沿用翻译用的 `apiTimeout`（`COpenAI.py:86`，**默认 300s**）；每个 token 失败**重试 2 次**（`COpenAI.py:262`）→ 最坏 2×300s；`_check_stage_model_availability`（`server_backend.py:181-183`）再串行对每个阶段 profile 各跑一轮 |

### 2.2 证据

`release/GalTransl_0.4.9_win/理狂人/GalTransl.log`：

```
19:20:46 Testing key1---sk-Wt7...A5SI---z-ai/glm-5.3
19:21:25 [并发] 获取API token sk-Wt7...A5SI 可用 1/1      ← 单次探活 39s > 前端 30s
```

另一处 `16:52:39 → 可用性检查失败，正在重试 1/2 次…` 显示单次失败约 9–10s，两次重试即 ~19s。用户 0.4.9 构建版实测，0.5.0 源码同源未修。

**放大效应**：`TranslateConsole.tsx:403-406` 检测失败自动重试（`MAX_AUTO_RETRIES = 3`、间隔 10s），每次重试都让后端重跑整轮检测。

### 2.3 改动方案

| 文件 | 改动 |
|---|---|
| `desktop/src/lib/api/general.ts` | `checkModelAvailability` 增加 `timeoutMs`（暂定 60000，与后端最坏耗时对齐，见 §2.4） |
| `GalTransl/COpenAI.py` | `checkTokenAvailablity` 增加可选参数（`max_retries` / `timeout`，**默认值保持现值**→ 翻译期零回归）；`_check_token_availability_with_retry` 接受覆盖值 |
| `GalTransl/server_backend.py` | 两条检测路径（`_check_model_availability`、`_check_stage_model_availability`）调用时传「检测专用上限」：单请求超时封顶（暂定 30s）、重试降为 1 次 |
| `desktop/src/pages/translate/TranslateConsole.tsx` | 把「超时 / 网络不可达」与「检测失败」区分：超时不计入 `error` 态、不触发自动重试（避免前端反复放弃、后端反复空转） |

**不新增配置键**：检测超时用代码内常量（如 `_AVAILABILITY_CHECK_TIMEOUT_CAP = 30`），避免给用户增加无意义旋钮（以新增冗余为耻）。

### 2.4 潜在 bug 与防范

| 潜在问题 | 防范 |
|---|---|
| 改 `checkTokenAvailablity` 默认行为 → 影响翻译期 `ensure_model_available_if_needed` | 新参数全部**默认沿用现值**，仅 server 检测路径传覆盖值；补回归测例锁默认值 |
| 后端封顶 30s 仍可能被多阶段 profile 累加超过前端 60s | 前端超时按「30s × 阶段数」估算或后端返回部分结果；本期先按「≤2 个阶段 profile」估算 60s，并在多阶段时打印耗时日志（`LOGGER.info` 检测耗时） |
| 前端把超时当成"检测中"却不重试 → 状态长期停在 checking | 明确 UI 文案（如"检测超时，后端仍在检测"）+ 提供手动重试按钮（复用现有入口） |

### 2.5 测例

| 层 | 测例 |
|---|---|
| 前端 | `checkModelAvailability` 发起请求时断言带 `timeoutMs`；超时错误不进入 error 态、不排定时重试 |
| 后端 | mock OpenAI client，断言检测路径传入的 `timeout` 被封顶、重试次数为 1；断言翻译路径（不传参数）仍为原默认值 |

### 2.6 日志

| 位置 | 级别 | 内容 |
|---|---|---|
| 检测开始/结束 | `LOGGER.info` | 检测对象（profile 名 / key 掩码）+ 耗时，便于下次定位 |
| 单 token 超时 | `LOGGER.warning` | 已有（`可用性检查失败，正在重试`），保留 |

## §3 缺陷三：`backend_profiles.yaml` 无生产者 + 打包版程序目录口径分裂

### 3.1 根因（两条独立缺陷，共同导致 `stageBackends` 必然失败）

**3a 数据源断裂**：「后端配置」页只写 localStorage，后端只读文件，两侧从未打通。

| 侧 | 位置 | 行为 |
|---|---|---|
| 前端写 | `desktop/src/lib/api/preferences.ts:202` | `writeBackendProfilesStorage` 只 `localStorage.setItem` + 派发自定义事件，**无任何 HTTP 调用** |
| 后端读 | `GalTransl/server_backend.py:357,415` | `_read_backend_profiles()` 读 `<程序目录>/backend_profiles.yaml`，文件不存在即返回 `{"profiles": {}}` |
| 端点 | `server_handlers_root.py:152,458,540` | GET/PUT/DELETE `/api/backend-profiles` 均存在，但 **desktop/src 全仓搜索无任何调用**（`grep "api/backend-profiles" desktop/src` = 0 命中） |

→ 结论：该 yaml **在整个系统里只有消费者、没有任何生产者**。用户"从来没有过这个 yaml"是必然结果，且与最近 20 次提交无关 —— `stageBackends` 与 `_resolve_stage_backend_profiles` 的 fail-fast 由 `2ddfacf`（0.4.5「四大阶段独立 API」）引入，缺口自那时就存在；此前未暴露只是因为项目 config.yaml 里 `stageBackends` 全为空值（空值会被 `continue` 跳过）。

**3b 打包版程序目录口径分裂**（本轮实测确认）：

| 用途 | 代码口径 | 打包版实际落点 |
|---|---|---|
| Dict / translation_guidelines / plugins | `os.path.abspath("Dict")` 等相对路径（`server_dict.py:271`、`server_meta.py:128`） | **cwd = 程序根** ✅ 实测 `GET /api/translation-guidelines` 返回 release 目录下真实文件 |
| app_settings.json | `AppSettings.py:16` `dirname(dirname(abspath(__file__)))` | `%TEMP%\_MEIxxxxxx`（临时解包目录）❌ |
| backend_profiles.yaml | `server_backend.py:357` 同一口径 | 同上 ❌ |

实测（启动 release 打包后端，端口 12399）：

```
PUT /api/backend-profiles/__probe__  →  {"success": true}
落点：C:\Users\19342\AppData\Local\Temp\_MEI120242\backend_profiles.yaml
      （release 根、工作区根均无此文件）
PUT /api/app-settings                →  落点：%TEMP%\_MEI113762\app_settings.json
```

`galtransl_backend.exe` 为 **PyInstaller onefile**（`galtransl_backend.spec:23-42`，仅单个 exe、`runtime_tmpdir=None`），模块 `__file__` 指向 `sys._MEIPASS` → 该路径**每次启动都不同、退出即删**。即：打包版下这两类配置**写了也存不住**；`%TEMP%` 下已残留 2 份历史 `app_settings.json`，说明该问题长期存在（用户此前跑打包版的设置其实一直在丢）。

### 3.2 证据汇总（可直接复核）

| 结论 | 复核方式 |
|---|---|
| `stageBackends` 解析失败 | `error.log` 多条 `ValueError: stageBackends.metadata|translate 引用的后端配置 '纪元律动'|'线衣' 不存在…（当前可用：无）` |
| 前端不写后端文件 | `grep "api/backend-profiles" desktop/src` → 0 命中 |
| 打包版落点 | 本轮探针实测（§3.1 表） |
| 测试为何没覆盖 | `tests/test_stage_backends.py` 全是**纯单元测试**，直接给 `_resolve_stage_backend_profiles(stage_map, profiles_dict)` 喂 dict，**绕过了 `_read_backend_profiles()` 这一真实数据源**；`tests/test_backend_profiles.py` 只测 patch 到 tmp 的读写 roundtrip |

### 3.3 改动方案（按 §0 决策点 1、3）

**A'（建议）：前端保存时同步 PUT，后端文件成为执行期唯一真源**

| 文件 | 改动 |
|---|---|
| `GalTransl/Utils.py`（或 `AppSettings.py`） | 新增 `resolve_app_dir()`：frozen 时 `dirname(sys.executable)`（若该目录名为 `backend` 再取上一级，兼容 exe 与 backend 同级两种布局），非 frozen 时保持 `dirname(dirname(abspath(__file__)))`。**与 `server_dict.py:271` / `server_meta.py:128` 的 cwd 口径在两种模式下结果一致**（已核对：开发模式均为项目根，打包版均为 release 根） |
| `AppSettings.py:16`、`server_backend.py:357` | 改为调用 `resolve_app_dir()`（消除两处重复实现） |
| `desktop/src/pages/backends/BackendProfilesPage.tsx` + `lib/api/preferences.ts` | 保存/删除 profile 时，除写 localStorage 外，同步调用 `PUT /api/backend-profiles/:name`（新增 `lib/api` 薄封装 + 失败提示） |
| `GalTransl/server_backend.py:421` | `_read_backend_profiles` 的 `except Exception` 分支补 `LOGGER.warning`（YAML 损坏时不再静默返回空） |
| （决策点 3 若采纳）`server_dict.py:271`、`server_meta.py:128`、`Utils.py:32` | 相对路径改为 `os.path.join(resolve_app_dir(), ...)`，去掉对 cwd 的隐式依赖 |

### 3.4 潜在 bug 与防范

| 潜在问题 | 防范 |
|---|---|
| 首次升级用户 localStorage 有数据、后端文件为空 → `stageBackends` 仍报错 | 打开展示「后端配置」页时做**一次性补齐**：把 localStorage 中尚不存在于后端的 profile 逐个 PUT（幂等，失败不阻塞 UI） |
| 前端 PUT 异步失败被静默吞掉 → 回到"无生产者" | PUT 失败必须 toast 提示并保留 localStorage 数据（双重保险） |
| 多实例/多窗口并发写 yaml | `_write_yaml_file` 已是原子写（tmp + `os.replace`，`server_config_schema.py:59-64`）✅；并发覆盖风险低，暂不加锁 |
| 模块级循环导入（Utils ↔ AppSettings） | `resolve_app_dir()` 放在 `Utils.py`（当前无 GalTransl 内部依赖），AppSettings / server_backend 单向引用 |
| 打包版路径变更后用户旧配置"迁移" | 无需迁移：旧数据本就在 `_MEIPASS` 且已随重启丢失，无损失 |
