## §2 架构设计

### 2.1 形态对比（决策点 1）

| 维度 | **A：进程内 HTTP 端点 + stdio 哑桥** | B：独立 stdio 进程 + 官方 SDK |
|---|---|---|
| 工具实现调用方式 | **进程内直调** `JobRegistry.submit()` / `RUNTIME_*` / `_collect_cache_files()` | 进程外，**只能** HTTP 打 `127.0.0.1:12333` |
| 与 `0.5.0修改计划.md:192` 原则 | 一致（"不学上游打自家 REST"） | 违背 |
| 0.6.0 内置 agent 复用 | **同一份工具实现直接复用** | 需重写一遍 |
| 新依赖 | **零**（标准库 `urllib` 足够） | 需装 `mcp`（venv 当前未装） |
| 协议正确性 | 需自写 JSON-RPC 分发（**核心仅 4 个方法**，字段已核实） | 由 SDK 保证 |
| 后端未启动 | 端点随后端存活，天然不存在该问题 | 需额外处理"后端没开" |
| 架构一致性 | 与现有手写路由 + 手写响应同构 | 引入 SDK 依赖与另一套生命周期 |

**建议 A**。核心理由：工具实现必须能直接调进程内业务对象（否则 0.6.0 内置 agent 要重写一遍），而 stdio 是进程级传输、无法在长驻后端进程内实现 —— 故用**哑桥**（只做 stdio↔HTTP 的 JSON-RPC 转发，不 import 任何业务代码）补齐 stdio 客户端兼容。桥约 60 行，零依赖。

### 2.2 定案形态（建议）

```
外部 MCP 客户端（CodeBuddy / Claude Desktop / Cherry Studio ...）
   │
   ├── (a) 支持 HTTP：直接连 http://127.0.0.1:12333/mcp
   │
   └── (b) 仅支持 stdio：命令行拉起 run_mcp_stdio.py（哑桥）
                              │ 逐行 JSON-RPC 转发
                              └──→ http://127.0.0.1:12333/mcp
                                        │
                    GalTransl/server_mcp.py（JSON-RPC 2.0 分发）
                                        │ 进程内函数调用（无 HTTP 自调用）
                          ┌─────────────┴─────────────┐
                    mcp_tools.py（工具定义+实现）   server_search.py（新增检索层）
                          │                            │
        JobRegistry / RUNTIME_REGISTRY /  _search_cache_entries / _search_source_scripts
        server_meta / server_dict / server_cache     / _search_dict_entries
```

## §6 风险与潜在 bug（含防范）

| # | 风险 | 分析与防范 |
|---|---|---|
| R1 | **`_read_json_body()` 只接受 object**（`server.py:262-268`），MCP batch 请求是数组 → 抛 `ValueError` | MCP 分支**不复用** `_read_json_body`，改用独立读体；显式检测数组并返回 JSON-RPC `-32600 Invalid Request`（MCP 现已弃用 batch） |
| R2 | **协议版本协商**：客户端发的 `protocolVersion` 可能不在本实现支持集 | 支持集内回显，否则**回退到自身最高支持版本**（规范允许），并 `LOGGER.warning` 记录；实现前先查官方 spec 确认版本标识（见 §10） |
| R3 | **`notifications/initialized` 无 id**，若按普通请求处理会写出 `"id": null` 响应 → 部分客户端报协议错 | 分发层按"无 `id` 即通知"处理：执行副作用后**不写响应** |
| R4 | **作业异常破坏协议**：`submit()` 会抛 `ValueError`（同项目已运行 / translator 非法）与 `_ConcurrentLimitError` | 统一在 `call_mcp_tool` 捕获 → `CallToolResult(is_error=True)`（工具级错误），**不**冒泡成 HTTP 500 |
| R5 | **搜索性能**：`_collect_cache_files` 递归 + 逐文件解析，大项目全量搜索慢，可能超客户端超时 | 强制 `max_results`（默认 200/硬顶 2000）+ 提前中断遍历 + 返回 `truncated`；`LOGGER.info` 记录耗时 |
| R6 | **`/cache/search` 抽函数后行为漂移** | 沿用现有测试锁；另加"同输入双路径等价"对比用例（旧端点 vs 新函数） |
| R7 | **H 内容外泄**：MCP 读路径完全绕过 H 门禁（原设计门禁只在"内置 agent 侧"） | 0.5.1 在 `mcp_tools.py` 预留单一拦截点 `_apply_h_filter()`（默认恒等）；0.6.1 接入 `hLevels` + `hCheckDict` + `is_h_value`。**这是本计划最需要用户裁决的架构项** |
| R8 | **`importlib.reload(server)` 不重载子模块**（0.4.10 铁律） | `server_mcp.py` / `server_search.py` 若有模块级缓存必须导出 `reset_caches()`，并在 `server.py` import 段调用；`route_mcp` 以参数接收 `registry`，不持有模块级全局 |
| R9 | **工具 schema 与实现漂移**（列了工具却没实现，或反之） | 单测：`set(MCP_TOOL_DEFS) == set(分发表)`；每个 def 必须含 `name`/`description`/`input_schema` 且 `input_schema.type == "object"` |
| R10 | **stdio 桥阻塞/缓冲**：桥若不 flush，客户端收不到响应 | 桥内每写一行即 `flush()`；读侧按行迭代（`MCP stdio 分帧格式须先核实`，见 §10）；`Content-Length` 分帧若被规范要求则需实现 |
| R11 | **文件超 2000 行硬约束** | `mcp_tools.py` 预估 600 行、`server_search.py` 预估 350 行，均在限内；批次 5 提交前跑行数检查 |
| R12 | **测试桩数据结构与生产不一致**（0.5.0 三次踩坑之三） | 检索层单测的桩**必须用真实缓存条目结构**（`pre_src`/`pre_dst`/`problem`/`name`），不得用 `[f"词{i}"]` 类简化桩 |
